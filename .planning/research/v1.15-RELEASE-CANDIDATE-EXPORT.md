# v1.15 Research: Verifiable Release Candidate Export and Handoff

**Researched:** 2026-07-29
**Scope:** Retained target-local addon candidates, external handoff evidence, atomic promotion, and strict cleanup authorization.

## Existing System Baseline

- `preflight_release_candidate` is a closed temporary lifecycle. Its public success requires artifact validation plus verified exactly-once cleanup. It must remain unchanged.
- The production Node lifecycle already provides complete two-root inventory, ordinal identity collision checks, source observation before and after copy, streamed SHA-256 comparison, candidate topology reconciliation, sensitive-text coverage, deterministic manifest generation, and a canonical combined digest.
- The remote lifecycle already executes entirely on the target Windows host and normalizes hostile or malformed transport results before they reach the MCP result.
- The result layer already treats adapter narration as untrusted and recomputes success from normalized evidence. The export result should use the same pattern instead of trusting an `ok` field from a remote script.
- Current Windows support already has target-native reparse classification and Windows file identity checks that can be extended to export roots, staging paths, destinations, handoff manifests, and cleanup targets.

## Platform Findings

### Same-filesystem promotion

- Node `fsPromises.rename(oldPath, newPath)` delegates to the operating-system rename operation. Cross-device moves fail instead of becoming a copy-and-delete operation.
- .NET `Directory.Move` reports an error when asked to move a directory to another volume.
- Creating staging state as a direct child of the validated export root and promoting it to a non-existent sibling destination therefore supplies a fail-closed same-filesystem boundary.
- Promotion evidence must record the staging parent identity, destination absence immediately before promotion, the exact rename or directory-move command, and post-promotion destination identity.

### Windows unsafe path types

- Windows exposes `FILE_ATTRIBUTE_REPARSE_POINT` for entries with an associated reparse point. Junctions and symbolic links must be rejected rather than followed.
- Ordinary `lstat` semantics are insufficient for the project’s Windows contract. Local Windows and remote Windows should reuse target-native attribute and file-identity probes.
- Every existing ancestor from export root through destination parent must be checked. A safe final leaf is insufficient when an ancestor redirects resolution.

### Ownership and cleanup

- Cleanup cannot rely on path ownership alone because a path can be replaced after export.
- A versioned external handoff manifest should bind the canonical export root, canonical destination, candidate identity, ownership identifier, addon name, file count, canonical combined SHA-256, source boundaries, target kind, creation operation, and boundary declarations.
- The ownership identifier is non-secret deletion evidence. It is not a remote credential and grants no target access.
- Cleanup must independently re-inventory the retained candidate, recompute the combined digest, re-read the external manifest, re-check canonical identities, and compare all caller-supplied cleanup assertions before any mutation.

## Recommended Contract

### `export_release_candidate`

Required input:

- `target`
- `addonName`
- `exportRoot`
- `destination`

The destination must be a direct child of the canonical export root. Both values are target-local paths. The destination and derived handoff manifest path must not already exist.

The handoff manifest path is derived deterministically as a sibling of the candidate directory: `<destination>.dota-workshop-handoff.v1.json`.

### `cleanup_exported_candidate`

Required input:

- `target`
- `exportRoot`
- `destination`
- `ownershipId`
- `manifestVersion`
- `combinedSha256`
- optional `dryRun` with default `true`

Dry-run performs every validation and reports whether deletion would be permitted. Execute performs the same validation, deletes only the verified candidate and its exact sibling handoff manifest, and proves their absence separately.

## Safety Decisions

- Reject an export root or destination at or inside a Dota root, source addon tree, repository root, volume root, user profile root, system directory, temporary-system root, or a directory with a `.git` ancestor marker.
- Reject parent traversal, non-absolute paths, NUL or newline content, alternate path spellings that canonicalize outside the root, case-fold collisions, symbolic links, junctions, reparse points, sockets, devices, FIFOs, and unknown entry kinds.
- Refuse any existing destination, existing handoff manifest, or unknown partial state. There is no overwrite flag.
- Never retry after partial promotion, mix observations from multiple attempts, repair source content, change targets, or fall back from remote to local execution.
- On export failure, remove only the staging directory and temporary manifest owned by the current operation. Never remove a pre-existing or promoted destination as generic failure cleanup.
- Remote export and cleanup remain on the target Windows host. Only normalized evidence returns to the MCP host.

## Test Strategy

- Reuse v1.14 fixture builders and integrity assertions to prove identical source and manifest semantics.
- Add adversarial fixtures for existing destinations, dangerous roots, path escape, reparse ancestry, case-fold collisions, source mutation, candidate mutation, digest mismatch, promotion failure, cleanup failure, and hostile remote envelopes.
- Add parity vectors that normalize fixture, local Windows adapter, SSH, and PowerShell Remoting results to the same public contract.
- Keep direct regression assertions around the exact `preflight_release_candidate` schema, boundaries, cleanup requirement, tool routing, packaged runtime, and test fixtures.
- Real Windows evidence is supplemental. Contract tests must never be described as proof of real NTFS or remoting behavior.

## Dependency Decision

No new runtime dependency is needed. Node filesystem and crypto primitives plus existing PowerShell/.NET capabilities cover the required operations.
